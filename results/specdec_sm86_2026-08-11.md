# Speculative decoding for K3 on RTX 3090 — what now works, and the one blocker left

Measured 2026-08-11 on 2×RTX 3090 (sm_86), vLLM main `dev627+g4988df2eb`,
4-layer synthetic K3 slice with a matched miniature DSpark draft, dummy weights.

## Headline: it was blocked on ALL of Ampere, not just under PP

We set out to make DSpark work under pipeline parallelism. Along the way the
decisive measurement showed the problem was one level deeper: **speculative
decoding could not run on sm_86 at all**, with or without a pipeline.

Proof it is not PP-related: the identical failure reproduces at **PP=1, on a
single GPU**.

### The mechanism, measured

A probe placed immediately before the kernel call in `TritonMLAImpl.forward_mqa`
printed:

```
[MQA] causal=True q=(768, 8, 576) bt=(256, 8) sl=(256,) ndecodes=256 ndtok=768
```

`q` carries one row per decode **token** (768); `block_table` carries one row per
**sequence** (256). Speculation makes `query_len = 768/256 = 3`. Upstream expands
the tables only inside `if not attn_metadata.causal:` — the non-causal DSpark
block path — so on the ordinary **causal** verification path the kernel indexes
512 rows past the end of `block_table`:

```
RuntimeError: Triton Error [CUDA]: an illegal memory access was encountered
  triton_mla.py:305 forward_mqa → triton_decode_attention.py:534
```

This never surfaces on Hopper/Blackwell because those use different MLA decode
kernels. **TRITON_MLA is the only MLA decode backend Ampere has**, so the whole
speculative path was closed on 3090.

### The fix (patch A6)

Mirror upstream's own non-causal flattening, but give each row the prefix that
belongs to it: row *j* of a sequence sees `seq_len - (query_len - 1 - j)`. Each
row then becomes an independent query over its own prefix, which *is* causal
semantics — no extra masking required.

**Result: GATE 1 PASS at PP=1.** The engine survives, serves, and reports
`SpecDecoding metrics: Mean acceptance length: 1.00, Drafted throughput: 2.11
tokens/s`. Acceptance of 1.00 is expected and not a defect here: the draft has
random dummy weights, so its proposals never match.

## Pipeline parallelism: the taps arrive, the engine then hangs

At PP=2 the draft's tap probe fired with:

```
[DSPARK_PROBE] shape=(768, 4096) ...
```

`4096 = 4 taps × 1024`. All four taps reached the draft, **including the two
computed on rank 0** — which before the B-patches were discarded at the stage
boundary. The tap-carrying mechanism works across GPUs.

Then the engine hangs. Stacks (via `faulthandler`, since ptrace is blocked in the
container) show both ranks inside warmup's `_run_decode_step`, with one blocked
in a PP send/recv (`gpu/pp_utils.py:83` → `distributed_c10d`) and the other ahead
in `eplb_utils.py`.

### Localised: rank 0 never leaves the prefill phase of warmup

Stacks were unavailable in the container (ptrace blocked; `faulthandler` produced
nothing on SIGABRT), so progress milestones were used instead. They settle it:

```
[WM] rank=1 ENTER warmup_kernels
[WM] rank=0 ENTER warmup_kernels            <- both enter
[WM] rank=1 PREFILL PHASE DONE, entering decode steps
                                             <- rank 0 never prints this
[WARMUP] rank=1 step=0/5 ...                 <- rank 1 proceeds, then blocks
```

**Rank 0 hangs inside the prefill phase of `warmup_kernels`; rank 1 completes
prefill, enters decode step 0, and blocks waiting for activations rank 0 will
never send.** A mutual wait across two different phases.

Note this refutes the earlier hypothesis (kept here deliberately): the divergence
is *not* the decode-step count, and not the sampler/drafter asymmetry inside the
step loop — rank 0 never reaches the loop at all. Two other plausible hypotheses
also died on measurement this session: EPLB (every path is gated on
`enable_eplb`, which we never pass) and speculation depth (`num_speculative_tokens
1` fails identically to 3).

Narrowing it further needs milestones *inside* the prefill phase — the next
cheap step.

## Honest status against the goal

| Claim | Status |
|---|---|
| Spec decode runs for K3 on sm_86 | **PROVEN** at PP=1, gate passed, drafts generated |
| The blocker was the attention backend, not PP | **PROVEN** — identical failure at PP=1 on one GPU |
| Hidden-state taps cross PP boundaries | **PROVEN** — 4096-wide tensor at PP=2, two taps from the other rank |
| Taps are *bit-identical* to PP=1 (Gate 2) | **NOT PROVEN** — PP=2 hangs before a comparable request completes |
| End-to-end spec decode under PP | **NOT PROVEN** — rank-asymmetric hang in warmup |
| Acceptance rate / speedup | **NOT MEASURED** — needs real weights, not a dummy draft |

### A near-miss worth recording

An earlier read of `probe_pp1.txt` / `probe_pp2.txt` showed *identical*
fingerprints and looked like Gate 2 passing. Checking file timestamps showed both
files were left over from the previous run, in which the gate and the reference
were **both PP=1** — a degenerate comparison that had to match. The stale files
were deleted. Always verify where the data came from before believing it.

## Next steps, in order

1. Fix the warmup divergence: make the spec-decode warmup step symmetric across
   PP ranks (or skip drafter warmup on ranks that have no sampler).
2. Then Gate 2: tap fingerprints at PP=2 vs PP=1 in one run, with a
   position-weighted checksum so reordering is detectable.
3. Then PP≥3 — at PP=2 there is no middle rank, so the receive-and-forward branch
   never runs; at PP=47 that is 45 of 47 ranks (see `DSPARK_PP_DESIGN.md`).
4. Only then measure acceptance and speedup, on real weights.

A6 is worth upstreaming on its own: it unblocks speculative decoding for every
Ampere user of MLA models, independently of everything above.
