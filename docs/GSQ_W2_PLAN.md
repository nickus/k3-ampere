# W2-чекпойнт K3: план производства (GSQ) — 2026-07-31

Источник: факт-чек по первоисточникам (workflow gsq-w2-factcheck) + наш
слайс-эксперимент. Serving-сторона уже валидирована (M1 + PR #48918).

## Вердикт по тулчейну: GSQ (IST-DASLab), форк

- Единственный инструмент с **реальным суб-3-битным артефактом триллионного
  масштаба**: Kimi-K2.5 (1T) @ 2.125 bpp с опубликованными evals
  (MATH500 96.7→97.3, LCB 61→69, но GPQA-D 89→77 — перекос калибровки).
- Его дефолтный ignore-list = дословно наш (роутед-эксперты only).
- Ships `convert_to_humming.py` — знает про наш серверный стек.
- GPTQ-инициализация + Gumbel-Softmax-рефайнмент — на 2 битах рефайнмент
  и есть продукт.
- llmcompressor отвергнут для мейн-рана: калиброванный путь = RAM-стена
  (~6-7 TB на 2.8T через run_compressed=False), бескалибровочный = RTN-only.
  Остаётся как формат-оракул и Track-A-дымовуха.

## 5.4 TB bf16-декванта НЕ нужно

Пайплайн послойный («модель никогда не грузится целиком»), деквант mxfp4 —
на лету, поэкспертно (~70 MB bf16/эксперт). Группа 32 (mxfp4) → 128 (W2)
делится нацело — без стыковых артефактов. Работа: `MXFP4PackedCompressor`
(~80 строк: E2M1-LUT + E8M0-скейлы; проверить порядок ниблов!).

## Треки

- **Track A (~$100, 1–2 дня): RTN W2 полного K3** через
  `llmcompressor.model_free_ptq` (шард-за-шардом, RAM ≈ шард×воркеры).
  Качество мусорное — цель: доказать конвейер и загрузку в vLLM+Humming
  на полном масштабе ДО трат на Track B. **Слайс-версия пройдена сегодня**:
  наш синтетический срез → oneshot W2 → корректный CT pack-quantized
  (I32-пак + BF16-скейлы g128, num_bits=2) — формат бьётся с PR-тестами
  дословно. Serve-проверка на боксе (ждёт пересборки колеса после
  torch-ABI-инцидента).
- **Track B ($2–5k, ~неделя): настоящий GSQ-ран.** Форк: `kimi_k3.py`
  (адаптация kimi_k25.py), MXFP4-ридер, патч бага `wbits=4` в
  inject_quantization_config (лейблит 2-битный ран как 4-битный!).
  Решающее число до аренды железа: Hessian на слой = E×d_in². Если
  эксперты едят латент 3584 → 896×3584²×4B ≈ 46 GB/слой (ок для 8×H100);
  если полный hidden 7168 → 184 GB/слой (нужно 16).

## Ресурсы полного рана

Диск 4–6 TB NVMe; RAM 0.5–1 TB; выход **~883 GB** → на 50×3090 остаётся
~277 GB под KV ✓. 93 слоя строго последовательно — resume через
progress.json обязателен (протестировать kill на 3-м слое в пилоте).

## Главные риски

1. Порядок ниблов/LUT mxfp4-ридера (тихий убийца — прецедент у
   kimi-k3-mlx: стоковая автодетекция мапит K3-метаданные неверно).
2. Качество: K3 MXFP4-QAT-нативен, bf16-мастера не существует — 2.125 bpp
   от 4.25 bpp информации. Единственный know-how против: рефайнмент + 
   разнообразная калибровка (GPQA-провал K2.5 — от матем.-скошенной).
3. Hessian-голодание: top-16/896 → ~1.8% токенов на эксперта; ниже ~d_in
   токенов Hessian сингулярен и GPTQ тихо деградирует в RTN. Калибровки
   нужно МНОГО (сотни тысяч токенов).
4. Ignore-list дрейф на невиданной GSQ архитектуре (KDA/MLA/LatentMoE/MTP).
